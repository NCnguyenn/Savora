Bạn là Antigravity, đóng vai trò Senior QA Engineer, System Analyst và Security Reviewer cho dự án Savora dùng PHP 8/MySQL/HTML/CSS/JavaScript.

NHIỆM VỤ DUY NHẤT

Thực hiện kiểm tra toàn diện hệ thống Savora và trả một báo cáo đánh giá trong câu trả lời cuối cùng. Bạn chỉ được kiểm tra, phân tích và báo cáo. Bạn KHÔNG được sửa lỗi, tối ưu, refactor, tạo bản vá hoặc thay đổi bất kỳ thành phần nào của dự án.

Hãy đọc và tuân thủ toàn bộ checklist tại:
docs/ANTIGRAVITY_READ_ONLY_AUDIT_CHECKLIST.md

RÀNG BUỘC READ-ONLY TUYỆT ĐỐI

1. Không sửa, tạo, xóa, đổi tên, di chuyển hoặc format bất kỳ file hay thư mục nào.
2. Không sử dụng apply_patch, editor save, sed -i, perl -pi, echo >, redirect ghi file, formatter hoặc code generator.
3. Không chạy git add, git commit, git checkout, git switch, git merge, git reset, git clean, git stash, git pull, git push hoặc bất kỳ lệnh Git làm thay đổi working tree, index, branch hay remote.
4. Không cài đặt, cập nhật hoặc gỡ dependency, package, extension, plugin hay database driver.
5. Không chạy INSERT, UPDATE, DELETE, REPLACE, CREATE, ALTER, DROP, TRUNCATE, GRANT, REVOKE, CALL hoặc procedure có thể ghi dữ liệu MySQL.
6. Không gọi API POST/PUT/PATCH/DELETE và không bấm nút giao diện có thể tạo đơn, cập nhật trạng thái, thanh toán, duyệt tài khoản, hoàn tiền, đổi cấu hình hoặc ghi audit log.
7. Không đăng nhập hoặc chạy route PHP nếu việc đó có thể tạo session, cập nhật last_seen, chạy migration, seed hoặc ghi database. Hãy đọc auth.php, db.php và session guard trước khi quyết định một kiểm tra runtime có thật sự read-only hay không.
8. Không chạy test PHP/MySQL nếu test đó ghi database. Nếu không chứng minh được test hoàn toàn read-only, phải bỏ qua.
9. Không tạo file báo cáo. Báo cáo chỉ được trả trong câu trả lời cuối cùng của bạn.
10. Không được sửa code dù lỗi rất nhỏ, lỗi hiển nhiên hoặc có thể sửa trong vài giây.
11. Không được tự ý “fix while reviewing”. Mọi đề xuất chỉ được ghi bằng văn bản trong báo cáo.
12. Nếu một bước kiểm tra cần phát sinh thay đổi, ghi rõ: NOT EXECUTED — READ-ONLY RESTRICTION, cùng lý do và bằng chứng tĩnh thay thế.

TRƯỚC VÀ SAU KHI KIỂM TRA

- Ghi lại kết quả git status --short trước khi bắt đầu.
- Chỉ dùng lệnh đọc như git status, git diff, git log, git show, rg/Get-Content, PHP lint, JavaScript syntax checking và các unit test đã xác minh không ghi file/database.
- Kết thúc bằng git status --short và git diff --exit-code.
- So sánh trạng thái trước/sau. Nếu có khác biệt do chính bạn tạo ra, dừng ngay và báo vi phạm; không tự sửa hoặc xóa để che giấu thay đổi.
- Không được đưa các file chưa được theo dõi có sẵn từ trước vào phạm vi chỉnh sửa.

MỤC TIÊU KIỂM TRA

Đánh giá liệu bốn vai trò Customer, Restaurant Owner, Delivery Driver và Admin đã đầy đủ, thống nhất và sẵn sàng vận hành cùng nhau hay chưa. Không chỉ đếm trang hoặc kiểm tra giao diện riêng lẻ. Phải truy vết dữ liệu và quyền sở hữu trạng thái xuyên suốt UI → JavaScript state → PHP endpoint → MySQL → UI của vai trò tiếp theo.

Hệ thống phải hỗ trợ tối thiểu:

1. Đặt món: Customer xem nhà hàng, xem thực đơn, tùy chỉnh món, thêm giỏ hàng, checkout và tạo đơn.
2. Theo dõi giao hàng: Customer theo dõi vị trí Driver bằng GPS thời gian thực hoặc GPS mô phỏng, với trạng thái giao hàng nhất quán.
3. Thanh toán: nhiều phương thức thanh toán trực tuyến/an toàn, wallet, cash/COD hoặc card theo đúng trạng thái tài chính.
4. Restaurant dashboard: Restaurant Owner cập nhật thực đơn, quản lý đơn hàng và xem thống kê doanh thu.
5. Admin: một tài khoản toàn quyền, giám sát và can thiệp có kiểm soát; Restaurant/Driver chỉ được tạo tài khoản sau khi Admin duyệt đúng hồ sơ.

PHẠM VI BẮT BUỘC

- 8 trang Customer.
- 11 trang Restaurant Owner.
- 5 trang Delivery Driver.
- 11 trang Admin.
- Shared headers, footers, stylesheets và JavaScript state modules.
- auth.php, logout.php, reset_password.php, admin_action.php, api/platform_state.php.
- db.php và toàn bộ lib/*.php liên quan schema, security, repository, action và session.
- Toàn bộ tests/*.test.js, tests/*.php và browser QA scripts, nhưng chỉ chạy test đã được chứng minh không ghi dữ liệu.
- MySQL schema, indexes, constraints, trạng thái, versioning, idempotency, audit, ledger, payment, dispatch, delivery và approval data model bằng SHOW/SELECT/information_schema read-only.

CÁCH ĐÁNH GIÁ

Mỗi trang phải được đánh giá theo: mục tiêu, thành phần UI, tương tác, validation, empty/loading/error state, responsive, accessibility, data source, quyền thao tác, route liên kết, backend/API tương ứng, bảng MySQL tương ứng và tác động đến ba vai trò còn lại.

Mỗi luồng phải được truy vết hai chiều:

- Ai tạo dữ liệu?
- Ai được phép cập nhật trường/trạng thái nào?
- Dữ liệu được lưu trong localStorage, session hay MySQL?
- Vai trò tiếp theo đọc dữ liệu từ đâu?
- Có nguy cơ hai nguồn dữ liệu khác nhau hoặc stale state không?
- API có kiểm tra role, CSRF, session, input, giá tiền, transition, version và idempotency không?
- Admin can thiệp có audit log, reason, optimistic locking và thông báo cho vai trò bị tác động không?
- Refresh hoặc đăng nhập lại có giữ được trạng thái thống nhất không?

Đặc biệt kiểm tra các chuỗi nghiệp vụ sau:

1. Restaurant/Driver application → document verification → Admin approval → user/profile creation → login/access.
2. Restaurant menu publish/update/availability → Customer catalog → cart → checkout.
3. Customer checkout → authoritative pricing → payment → order/order items → Restaurant live orders.
4. Restaurant accept → preparing → ready for pickup → dispatch creation.
5. Driver offer/accept → delivery creation → arrived → picked up → delivered.
6. Delivery status/GPS → Customer tracking → Restaurant order history → Admin monitoring.
7. Cash/card/wallet payment → wallet/payment/ledger/COD/refund/payout consistency.
8. Customer/Restaurant/Driver incident → Admin case → evidence/request information → resolution/refund.
9. Admin suspend/block/revoke/reset → active sessions của tài khoản bị tác động.
10. Admin promotion/fee/service area/settings → Customer checkout và các vai trò liên quan.

KHÔNG SUY ĐOÁN PASS

- Chỉ đánh dấu PASS khi có bằng chứng cụ thể.
- Nếu chỉ có UI nhưng không có backend: PARTIAL hoặc FAIL.
- Nếu chỉ có localStorage nhưng trang khác đọc MySQL: ghi rõ split-brain/stale-data risk.
- Nếu một nút không có handler, API hoặc persistence tương ứng: FAIL.
- Nếu code tồn tại nhưng không có đường gọi thực tế: UNREACHABLE.
- Nếu không thể chạy vì read-only: NOT EXECUTED — READ-ONLY RESTRICTION.
- Không dùng số test cũ hoặc báo cáo cũ như bằng chứng duy nhất; phải kiểm tra source hiện tại.

MỨC ĐỘ LỖI

- BLOCKER: Không thể hoàn thành chức năng cốt lõi hoặc hệ thống không thể vận hành.
- CRITICAL: Sai quyền, sai tiền, mất dữ liệu, bypass approval, account/session compromise hoặc trạng thái đơn nghiêm trọng.
- HIGH: Luồng chính bị đứt, dữ liệu giữa vai trò không thống nhất, thao tác không bền vững sau refresh.
- MEDIUM: Một phần chức năng/validation/error handling/accessibility không hoàn chỉnh nhưng có workaround.
- LOW: Copy, spacing, visual inconsistency hoặc vấn đề nhỏ không chặn nghiệp vụ.

ĐỊNH DẠNG BÁO CÁO CUỐI CÙNG

Viết báo cáo bằng tiếng Việt, giữ nguyên tên route, table, field và function bằng tiếng Anh. Báo cáo phải có:

1. Executive Summary.
2. Read-only compliance: git status trước/sau, lệnh đã chạy, lệnh bị bỏ qua.
3. Readiness verdict: READY, READY WITH CONDITIONS hoặc NOT READY.
4. Inventory đủ 35 trang, không gộp thiếu trang.
5. Feature coverage cho đặt món, GPS, thanh toán và Restaurant dashboard.
6. Ma trận đồng bộ bốn vai trò.
7. Báo cáo từng luồng end-to-end.
8. Backend/API review.
9. Database/schema/integrity review.
10. Security/authorization review.
11. UI/UX/accessibility/responsive review.
12. Automated-test coverage và khoảng trống kiểm thử.
13. Findings sắp xếp BLOCKER → CRITICAL → HIGH → MEDIUM → LOW.
14. Danh sách chức năng còn thiếu hoặc chỉ là demo/local state.
15. Kết luận hệ thống đã sẵn sàng cho demo, UAT và production ở mức nào.

Mỗi finding phải có:

- ID và severity.
- Tiêu đề cụ thể.
- Vai trò/trang/luồng bị ảnh hưởng.
- Evidence dạng file:line, function, SQL table/field hoặc test name.
- Expected behavior.
- Actual behavior hoặc static evidence.
- Data/security/business impact.
- Reproduction hoặc trace steps ở chế độ read-only.
- Recommended direction bằng văn bản, tuyệt đối không triển khai sửa chữa.
- Confidence: Confirmed, Strong evidence hoặc Needs runtime verification.

Nếu không tìm thấy lỗi ở một khu vực, vẫn phải ghi khu vực đã kiểm tra và bằng chứng PASS. Không được trả lời chung chung như “looks good”, “seems complete” hoặc “all tests pass”.

Kết thúc báo cáo bằng câu xác nhận chính xác:

“READ-ONLY AUDIT COMPLETED. No source code, configuration, Git state, API data, or database data was intentionally modified.”
